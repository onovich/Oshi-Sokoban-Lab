## 1. 课程单位

每个关卡组围绕一个内部命题，固定包含三种角色：

| 角色 | 玩家经历 | 机器验收 |
| --- | --- | --- |
| 建立关 `establish` | 通过一个最小但完整的谜题形成规则假设。 | 有解；关键事件不可绕过；关键事件后最多 3 次有效交互。 |
| 定界关 `boundary` | 只改变一个因果变量，修正最可能的过度概括。 | `contrastVariable` 明确；对应反事实测试通过。 |
| 推演关 `inference` | 面对表面不可能的布局，推出稳定规则的二阶后果。 | 有解；命题谓词不可绕过；关键事件后最多 6 次有效推动。 |

内部的 `LevelTheorem` 不显示给玩家。界面只显示胜利目标、操作、组别、阶段和进度；规则由盘面表达。

## 3. 解锁结构

```text
01 建立 → 02 定界 ─┬→ 03 推演（可稍后完成）
                    ├→ Shape: 04…15
                    ├→ Fake: 16…18
                    ├→ Spike: 19…27
                    ├→ Goal: 28…33
                    ├→ Rain: 34…39
                    └→ Gate: 40…48

已掌握的两个前置分支 → 49…63 的对应组合组
```

- 完成一个组的定界关即获得该组的理解标记。
- 组内严格按建立 → 定界 → 推演开放。
- “下一关”优先进入本组三关；第三关后选择最低编号、已解锁且未完成的关。
- 22–24 只有在 19–21 全部完成后才开放；这项完整前置不会阻止玩家游玩其它已开放机制分支。
- 高难推演关不阻断其它已开放分支，但全部 63 关完成才计完整通关。
- 关卡图可随时返回已解锁关；胜利后只显示“下一关”，不自动跳转。

组合组前置：

- 49–51：完整 footprint + Spike 原位
- 52–54：可移动 Goal + Rain 停止点
- 55–57：Rain 停止点 + Gate 远端条件
- 58–60：数字匹配 + Fake Block

## 4. 数据与分层

```ts
type LessonRole = 'establish' | 'boundary' | 'inference';

interface LevelTheorem {
  axioms: string[];
  proposition: string;
  requiredPredicates: string[];
  criticalEvent: string;
  contrastVariable?: string;
  readabilityElements?: string[];
}

interface LevelSpec {
  id: string;
  groupId: string;
  role: LessonRole;
  prerequisites: string[];
  board: BoardDefinition;
  theorem: LevelTheorem;
}

interface CourseGroupDefinition {
  prerequisites: string[];
  completionPrerequisites?: string[];
}

interface LevelAnalysis {
  solvable: boolean;
  optimalMoves: number;
  optimalPushes: number;
  insightTailPushes: number;
  bypassExists: boolean;
  proofCriticalElements: string[];
}
```

- `game-engine.ts` 只处理确定性规则和领域事件。
- `authored-course.ts` 只保存盘面和必须发生的可观察谓词。
- `course-catalog.ts` 只保存课程、公理、命题与依赖。
- `level-analyzer.ts` 通过公开引擎接口求解，不能复制另一套规则。
- React 表现层只消费状态和类型化事件；Gate 动画、补间、图标不参与胜负判定。
- Spike death reset 保持独立路径，不复用手动 Restart。
- `object-reset` 事件携带实际 `contactCells`；棋盘只据此播放进入 Spike、接触爆炸和 origin 重生三段演出，不生成 Spike 到 origin 的空间轨迹。
- Spike 关以低对比度图标层显示出生 footprint，不改变格子颜色；reset 演出锁定方向输入 620ms，但 Undo / Restart 可立即取消。

## 5. TDD 关卡门槛

提交候选关的顺序固定为：

1. 从作者裁定和 Unity 源码添加机制对照测试。
2. 先写 `LevelTheorem` 和失败的命题测试。
3. 编写最小盘面直到有解。
4. 禁止每个 `requiredPredicate` 再求解；仍有解即存在命题绕过。
5. 回放求解器路线，记录最短移动、推动、关键事件和顿悟尾巴。
6. 对证明关键实体和格子做删除 / 封墙变异；区分证明元素与表现边框。
7. 通过 [盲测协议](playtest-protocol.md) 后才能从候选池晋升为正式关。

测试分工：

- 求解器证明“可解”和“不能绕过指定可观察后果”。
- 变异测试证明地图元素不是无关填充。
- UI 测试证明内部命题和提示没有泄漏给玩家。
- 真人盲测证明玩家能从静态盘面与稳定反馈理解命题。

当前自动化门槛已经运行在 63 个候选盘面上；真人盲测仍为空，因此不能把当前列表描述成最终定稿。

## 6. 下一阶段：难度与技巧掌握

作者完整游玩旧 60 关后的判断是：当前谜题总体有趣、曲线平缓，但绝大多数约为 1–3 / 10，机制后果与技巧迁移尚未充分展开。下一阶段不以继续横向增加新机制为优先，而要纵向深挖已经稳定的规则。

- 正式课程需要覆盖 1–10 / 10 的完整难度谱，而不是只把现有关卡整体拉长。
- 一个重要技巧不能只经历一次三关组；它还要经过变式练习、反向验证、跨布局迁移、与其它已学技巧组合，以及高难综合应用。
- 高难关应要求玩家识别并组合多个已学技巧，但每个因果步骤仍须静态可读、规则稳定、可撤销验证。
- 既有三关组继续承担“建立—定界—首次推演”；后续可以为同一技巧建立进阶组与组合组，形成从熟悉到举一反三的纵向阶梯。
- 难度 8–10 的题目必须来自二阶／三阶后果、顺序依赖、推侧访问、拓扑或资源冲突，不以冗长搬运、读图歧义或试错成本冒充深度。
- 旧 60 关作为已验收的基础课程保留；新增高难内容应通过新的命题测试、求解／变异审计及独立验收进入课程。
