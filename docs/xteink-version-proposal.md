# LearnSokoban 阅星曈版本建议

日期：2026-09-23。状态：设计建议，尚未实现或真机验证。

## 判断

建议以参考项目使用的 X4 Pro 竖屏为首个目标，制作适合随手打开、慢慢推理、随时续玩的黑白机关谜题册。复用 Oshi 的空间规则和关卡研究，把表现与输入重做为设备端 Lua 应用。

推箱子的离散状态适合静态显示；真正的适配难点是物件叠层辨识、反复移动的操作成本，以及雨天滑行、Gate 穿越、Spike 回位在取消动画后如何保持因果清晰。设备版仍应保留这些有辨识度的机制，按阶段验证。

## 产品体验

进入应用直接继续当前关；首次进入提供短教学和跳过入口。无时间压力，步数只作记录。撤销是常用工具，重开在菜单中二次确认。通关后保留已完成棋盘，明确点击“下一关”才前进。

核心输入采用固定的大方向按钮，一次点击执行一次规则动作；能够提供方向事件的实体键走相同路径，实际按键映射需设备验证。首版不做长按连发、拖动推箱、滑动手势和自动寻路。雨天的一次动作可以是一次完整滑行，撤销仍回到本次输入之前。菜单和教学弹层必须截断底层输入。

“查看物件”是明确进入的独立模式：点物件查看编号、所属整块形状、覆盖情况、出生点或 Gate 配对，返回后继续移动。查看模式不改局面，不给出推荐动作。避免同一次点棋盘同时承担移动、选中和解释三种语义。

## 视觉方向

建议采用白纸上的黑白机械平面图，保留项目机械角色、箱体、机关的身份。角色用简洁机器人符号；墙是连续的厚边界；可推箱体有清晰外轮廓。废土氛围可用于开屏和章节插图，棋盘以占格和推侧识别为先。首版采用正交俯视图，3D 模型不是移植前置条件。

480×800 是参考项目布局基准，最终按目标设备确认。初稿可分成：顶部约 64px 放关号和菜单，中部约 440×440 放完整棋盘，再留约 60px 的说明区，底部约 200px 给方向和撤销控件。棋盘保持整数像素方格，小地图居中且限制最大格宽，不能把一行教学关拉满整页。

当前 authored-course 定义可见 9 列地图；以 432px 棋盘宽计算，每格 48px，可作为符号压力样例。不能因此宣称所有实验关都适配。每个候选关要单独计算布局，不裁切棋盘、不移动相机。过密关卡先退出首发目录，不能为了画面随意删墙改规则。

符号方案需用真实尺寸样张验证：

| 对象 | 建议表达 | 必须看得懂的关系 |
| --- | --- | --- |
| 玩家 | 小型机器人或人形黑色符号 | 与箱子区别明显，脚下地面标记仍可辨认 |
| 普通箱 | 粗轮廓、白色内面、中央编号 | 编号与是否达成目标是两种独立信息 |
| 多格箱 | 完整外轮廓，内部细接缝 | 一整件一起移动；L 形仍准确占据三个格 |
| 通配地面目标 | 四角定位符 | 与有编号目标不同 |
| 编号目标 | 地面内框加编号 | 只匹配相同编号，不能用装饰替代数字 |
| 可移动目标 | 地面目标基础上增加明确的可移动外形标记 | 能推或能穿取决于局面和输入方向，不能画成永久开关状态 |
| Fake Block | 明确的辅助箱徽记或缺角 | 参与碰撞和推动，但不计入通关 |
| Gate | 门形符号与独立配对字母 | 字母表达链接，不与目标数字混用；移动后配对保持 |
| Spike | 刺形符号；查看模式展示对应物件出生点 | 触刺尝试回位，不能暗示永久删除 |
| Rain | 页首固定的滑行模式标记 | 作用于全关，不画成局部积水格 |

箱压目标、玩家站目标、局部覆盖多格目标要分别出样张；边缘目标标记与内部箱编号需同时可读。完成标记不能把整个物件涂黑而盖住信息。减少密纹和全屏反白，避免用细碎装饰区分关键身份。

普通走动一步提交终态。滑行、传送、回位从已有 DomainEvent 提取简短结果，例如“箱子回到起点”；必要时在查看模式显示本步起终点。无持续雨线、闪烁提示和连续过渡动画。默认反馈描述已经发生的动作，不预测下一步或代替玩家判断远端条件。

## 关卡和教学

首发候选池从作者已验收的 60 关基础目录导出，保留稳定 ID、前置关系和关卡指纹；不能直接将 authored-course 内所有定义都视为生产目录。mastery-v2 的 70 个可玩盘面与开发实验应分别标识。现有高难教学验证尚未结束，不因移植而自动进入成品。

首个可玩版本建议 9–12 关，覆盖推动站位、多格整块移动、完整覆盖和数字匹配；具体名单在导出正式目录后确定。再制作内部机制验收包，分别覆盖可移动目标的推/穿、雨天邻接动作与滑行、Gate 远端阻挡、Spike 回位许可及撤销。机制验收通过后，再按教学前置关系扩展正式目录。

教学沿用“建立—定界—推演”。首次只教方向与撤销，用一个小谜题让玩家自己完成；新机制到首次出现时解释。将“footprint”等设计术语换成“这几个格是一整块”“整块都放到目标上才算完成”。不在开局说明中提前泄露暂存、让路等解题策略。

低刷新设备应减少理解后的机械执行，不能直接把难题换成短题。优先选布局紧凑、推理明确、领悟后收尾较短的关卡；需要修改冻结布局时创建独立设备变式 ID，并重新验证解法、核心条件和真人体验。

## 实现与验证

建议独立 worktree 和 `codex/xteink` 分支，在 `ports/xteink/` 下放 Lua 规则、应用、绘图、教学、设备目录、导出脚本和测试。当前 Web 的 TypeScript 内核是语义参照；设备实现独立 Lua 状态机，不能假定可以运行 React 或浏览器代码。

电脑端从正式目录导出确定性关卡，生成动作序列和逐步规范化状态。Lua 对照玩家位置、物件位置/出生点、编号与形状、胜负、动作是否生效和关键事件。参考解回放之外，必须覆盖错误输入、阻挡、异号覆盖、远端条件、无效回位、撤销与重开。设备只做一次动作结算与绘制，不运行搜索。

撤销使用可逆动作差量或有界历史，避免每步复制整套关卡数据；上限应实测后确定。存档包含版本、稳定关卡 ID/内容指纹、完整可变局面、已完成关卡、教学偏好；恢复后的撤销能力需明确设计和预算验证。退出重开、重新进入同一 VM、关机重启、应用更新分别验证，不能用桌面快照测试替代设备持久化结论。

原生文字先验证真实字宽；大标题如需定制，电脑端预制少量图片。不要启动时生成整套中文字库。按状态变化请求绘制，布局切换与普通动作分别测试刷新效果，最密棋盘、帮助页和叠层状态都计数绘图命令。

分四个交付节点：

1. 原尺寸黑白符号与布局样张：普通、多格、叠层、Rain、Gate、Spike。先解决看不清的问题。
2. 真实 Lua 9–12 关可玩样机：方向、撤销、重开、教学、恢复；与 TypeScript 状态对照。
3. 内部机制验收包及真机连续游玩：检查因果表达、误触、残影、输入积压、长会话内存和生命周期，再决定正式关卡扩展。
4. 内容与发布：官方 Studio 导入、核实实际入口版本、校验、保存、设备安装验证；最后制作商店材料。推送请求成功与安装启动成功分别记录。

## 当前项目边界

本次检查时工作区无未提交改动。交接资料仍列有 LAB36→LAB33 教学迁移试玩、采用原画落到模型以及机关原画待办；它们不构成黑白设备样机的技术前置。当前提案没有更改 Web 游戏、冻结关卡或 3D 实验，也没有创建 Studio 项目或向设备推送。
